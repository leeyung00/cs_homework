# 애플리케이션 계층
- 네트워크와 인프라의 존재 이유

## 1. 원리
- 네트워크를 통해 다른 종단 시스템과의 통신
- C나 파이썬, 자바와 같은 작성하여 종단 시스템에서 작동되어야 한다.

### 1-1 구조
- 클라이언트-서버 / P2P와 등과 같은 구조로 존재
- 클라이언트-서버는 서버가 알려진 고정 IP를 가지고 항상 동작해 있어 클라이언트가 필요할 때 언제든지 연결할 수 있게 한다. 
- P2P는 간헐적으로 연결된 호스트의 쌍으로 이루어져 상호작용을 하며 이용자가 늘어날 수록 망이 커지는 특징이 있다.

### 1-2 통신
- 각 종단 시스템은 네트워크를 통해 메세지를 교환하여 통신하며 이때 사용되는 프로그램을 프로세스라고 부른다.
- 프로세스는 소켓을 통해 메세지를 전달하거나 전달받는다.
  - 이 과정에서 필요한 것이 IP와 포트번호이다. IP는 메세지를 보낼 호스트의 주소이며 포트번호는 해당 호스트에서 실행되고 있는 프로세스의 소켓 번호이다.

### 1-3 이용 가능한 트랜스포트 서비스
- 애플리케이션 밑에서 작동하고 있는 트랜스포트 계층이 애플리켘이션 계층에게 제공할 수 있는 서비스는 신뢰적 데이터 전송, 처리율, 시간 보장, 보안이다.
  - 신뢰적 데이터 전송같은 경우에는 네트워크를 통해 이동하고 있는 데이터의 손실에 있어 신뢰적인 프로토콜(ex. tcp)을 사용하여 데이터의 신뢰성을 보장한다.
    - 이와 반대로 데이터의 손실을 일부 허용하는 서비스의 경우(ex. 화상통화) 비신뢰적인 프로토콜(ex. udp)을 사용할 수 있다.
  - 처리율이란 송신 프로세스가 수신 프로세스에게 전달할 수 있는 데이터의 비율을 나타내는 것으로 네트워크를 공유하는 인터넷 상에서 처리율은 계속해서 변한다.
    - 특정 프로세스는 처리율을 보장받기 바라며 이를 대역폭 민간 애플리케이션이라고 한다. 반대의 경우는 탄력적 애플리케이션이라고 한다.
  - 시간 보장이란 모든 데이터가 특정 시간내에 도착해야 하는 것을 보장한다. 이는 실시간으로 이루어지는 애플리케이션에서 중요하게 작동한다.
  - 보안은 송신자가 데이터를 보내면 해당 데이터를 암호화하여 데이터가 유출되더라도 안전하게 해야하며 수신자는 이 암호화된 데이터를 해독할 수 있어야 한다.
 
 ### 1-4 tcp / udp 서비스
- tcp는 연결지향적 서비스이다. 핸드쉐이킹 과정을 통해 두 종단 시스템의 연결을 확인하고 데이터를 보낸다. 또한 데이터를 신뢰적으로 보내기 위한 알고리즘을 사용하여 신뢰성을 확보한다.
- udp는 비연결형 서비스로 tcp와는 다르게 핸드쉐이킹 과정 없이 데이터를 전달하여 신뢰성을 보장할 수 없다. 하지만 이 덕분에 처리율이나 시간 보장 측면에서 갖는 이점이 존재한다.

### 1-5 프로토콜
- 애플리케이션 계층의 가장 대표적인 프로토콜은 HTTP 프로토콜이다.

### 1-6 종류
- 인기있는 인터넷 애플리케이션으로는 웹, 전자메일, 디렉터리 서비스, 비디오 스트리밍, P2P 애플리케이션이 있다.

## 2. 웹과 HTTP
- 현재 존재하는 대부분의 애플리케이션은 웹이라는 애플리케이션과 이를 다루는 HTTP 프로토콜로 이루어져 있다.

### 2-1 HTTP 개요
- 웹은 기본 html과 url을 통한 여러 객체들로 구성된다. 이때 http는 웹 클라이언트가 웹 서버에게 어떻게 요청하는 지와 웹 서버가 웝 클라이언트가 어떻게 데이터를 전송하는 지 정의한다.
  - 기본적으로 tcp프로토콜을 사용한다. 신뢰성을 보장받기에 서버는 요청을 한 클라이언트의 정보를 따로 저장하지 않는다. 그렇기에 http는 stateless하다.

### 2-2 비지속 / 지속
- tcp 상에서 각 요구/응답의 쌍을 같은 tcp연결에 보내는 것을 지속, 분리된 연결에 보내야 하면 비지속 연결이라고 한다.
- 비지속 연결의 경우 http 상에서 각 객체마다 새로운 tcp 연결을 하여 데이터를 전달 받는다.
  - 비지속의 경우 여러 데이터가 한 번에 보내져야 할 때 연결에 관한 오버헤득 발생하지만 일회성 데이터를 간혹 받는 경우에 자원을 아낄 수 있는 이점이 존재한다.
- 지속 연결의 경우 응답을 보내더라도 해당 연결을 유지하여 추가적인 데이터를 전달한다.
  - 지속 연결에 경우 한 번에 여러 데이터를 연결 오버헤드 없이 받을 수 있지만 일정 시간동안 tcp 연결을 지속하고 있기 때문에 필요 이상의 자원을 가지고 있는 경우가 존재한다.

### 2-3 HTTP 포멧
- 응답 메세지와 요청 메세지의 포멧이 존재하며 요청 메세지에는 GET/ POST/ HEAD/ PUT/ DELETE의 방식 필드를 가지며 응답 메세지에는 200/ 301/ 400/ 404와 같은 상태코드를 가진다.

### 2-4 쿠키
- 서버의 http는 기본적으로 stateless지만 사용자 맞춤 컨텐츠를 제공하기 위해서 사용자의 데이터를 저장하는 쿠키라는 개념을 사용한다.
- 쿠키는 사용자의 여러 데이터를 가지고 있기 때문에 개인 정보에 대한 주의가 필요하다.

### 2-5 캐싱
- 프록시 서버라고도 불리는 캐시는 종단 서버를 대신하여 http의 요청을 받는 서버이다. 캐시 서버는 최근에 호출된 객체의 사본을 저장해두어 종단 서버로 몰리는 트래픽을 완화해준다.
- 이 과정에서 캐싱된 객체가 적절한 객체가 아닐수도 있다. 서버에서 데이터가 바뀌었지만 호출된 적이 없으면 클라이언트는 과거의 데이터를 응답 받을 수 있기 때문이다.
- 이를 해결하기 위해 조건부 GET이 나타났다. 해당 동작은 요청이 들어올때 캐시 서버가 종단 서버에게 수정된 시간만을 요청하여 비교한다. 수정시간이 다르면 종단 서버로 해당 요청을 넘기고 아니면 자신이 응답한다.

### 2-6 HTTP/2
- http/1.1 이후 등장하여 기존 데이터 포맷 방식과 전송 방법을 변경하였다.
- 1.1은 하나의 tcp 연결상에서 데이터를 요청, 응답하기 때문에 HOL블로킹 문제가 발생하였다.
  - HOL블로킹이란 하나의 객체가 전송되며 뒤의 객체들의 전송이 지연되거나 전송되지 않는 문제를 말한다.
  - 이를 해결하기 위해서 같은 연결에 여러 병렬 소켓을 열어 뒤에 있는 객체들을 전송하여 해결하고자 하였다
    - 이 방법은 자원을 고갈시키는 위험이 존재한다.
- 2에서는 프레이밍을 통해 각 객체들을 고정된 길이의 프레임으로 나누어 각 객체의 프레임을 인터리빙 방식으로 전송한다.
  - 이에 더해 우선순위 조정을 통해 여러 요청에 대해 메세징 우선순위를 부여하고 프레임을 전송하여 애플리케이션의 성능을 최적화하였다.

## 3. 전자메일
- 전자메일의 구성 요소로는 사용자와 서버가 있으며 이를 위한 tcp를 활용한 smtp프로토콜이 존재한다.

### 3-1 SMTP
- 주요 특징으로는 점대점 연결로 사이에 다른 메일 서버를 사용하지 않는다. 
- 오래된 기술로 몸체가 7비트의 아스키코드여야 한다는 제약이 존재한다. 그렇기에 오늘날 이미지, 동영상과 같이 대용량 파일을 보낼 때 변환하여 보낼 필요가 존재한다.

### 3-2 포멧
- from과 to 헤더라인이 필수적이다.

### 3-3 프로토콜
- 메일 서버는 송신되는 메일을 수신하기 위해서 항상 소켓을 열어두고 인터넷과 연결돼야 한다는 제약이 발생한다.
- 이를 위해서 메일 서버는 일반적인 사용자들과 공유되는 메일 서버를 두고 개인 메일 서버는 이를 활용하는 에이전트의 역할을 가진다
- 개인 메일 서버는 이 공유 메일 서버에 접근하기 위해 http를 활용하거나 imap를 활용하여 접근한다.

## 4. DNS
- 인터넷은 호스트를 식별하기 위해 이름을 활용하거나 ip주소를 활용한다.

### 4-1 서비스
- 사람은 이름으로 식별하는 것을 선호하고 인터넷은 ip주소로 식별하는 것을 선호한다. 그렇기에 이름을 ip주소로 변환해 주는 프로토콜이 dns이다.
- dns 클라이언트와 서버는 udp로 통신하는 것이 일반적이다.

### 4-2 동작 원리
- 요청을 받은 dns는 해당 데이터를 dns 서버에 보내 그에 대응하는 ip주소를 응답받는다. 이후 주소를 호출한 애플리케이션에 전달한다.
- 이 과정에서 dns서버는 우선 로컬 서버로 보내진다. 로컬 서버는 수신받은 이름을 루트 서버로 보낸다. 루트 서버는 해당 이름에 대한 최상위 레벨 서버에 대한 주소를 알려주고 로컬 서버는 이 주소로 이름을 보낸다. 최상위 레벨 서버는 이 이름에 대한 책임 서버 주소를 보내고 로컬 서버는 다시 이 책임 서버에 이름을 보낸다. 그렇게 해서 최종 ip주소를 받아 애플리케이션에게 전달한다.
  - 해당 과정을 캐싱을 통해 줄일 수 있다.

### 4-3 레코드와 메세지
- dns서버는 매핑을 위해 name, value, type, ttl 4가지 필드를 포함한 튜플을 레코드로 저장해두고 있다.

## 5. P2P
- 기존 서버-클라이언트와 다른 구조로 간헐적으로 연결된 홋트들이 직접 통신하는 방식이다.

## 6. 분배 네트워크
- 비디오 스트리밍이 전체 인터넷 트래픽의 80%를 차지

### 6-1 비디오
- 전송률과 품질은 반비례 관계이다.

### 6-2 HTTP와 DASH
- http 스트리밍은 get요청을 통해 비디오를 받아오며 버퍼에 저장을 시작한다. 이 저장이 임계값을 넘으면 클라이언트에서 비디오가 재생되며 버퍼에 해당 비디오를 계속해서 수신받는다.
- 이 방식은 모든 클라이언트가 같은 품질의 비디오를 인코딩한다. 각 사용자마다 갖는 가용 대역폭이 다르기에 문제가 발생한다. 이를 해결하기 위해서 나오 것이 dash이다.
- 청크 단위로 작동하며 각 청크의 전송률은 각 사용자의 가용 대역폭에 따라 동적으로 변화한다. 이를 실현시키기 위해 매니패스트 파일을 통해 하나의 비디오에 품질을 각각 저장한다.

### 6-3 분배 네트워크
- 콘텐츠를 분배함에 있어 트래픽을 안정적으로 공급하기 위해 콘텐츠 분배 네트워크인 cdn서버를 운영하여 안정성을 높인다.
- 단일 데이터 센터에 요청이 많으면 문제가 발생하기에 여러 지역에 데이터 센터와 cdn서버를 설치하고 오는 요청을 분산하여 처리해주는 동작 방식을 지니고 있다.
